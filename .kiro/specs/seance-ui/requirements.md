# Spec: seance-ui

## Overview
A polished, haunting-but-usable web UI for Green Screen Seance (React + Vite + TypeScript in `web/`). Left: the live 3270 screen rendered faithfully as a 24x80 phosphor-green grid. Right: the seance chat. A **planchette** (ouija pointer) glides over the green screen to the field the agent is reading or filling, so people can see what the AI is doing. This is the signature of the project (judging.md, criterion 3 and 5).

The UI is a **view and a decision-maker**, not a terminal. It talks only to the agent's websocket and REST API (structure.md), using the protocol in `docs/contracts.md` sections 3 to 5. It cannot send raw keys. The one thing it can *do* to the legacy system is let the human approve or deny a pending action, so that modal is built as a safety control first and as a design piece second.

Normative formats (events, REST, shared shapes) are in `docs/contracts.md`; this spec must not contradict it.

## Requirements

### Layout and the green screen
- REQ-001: **Split view.** At widths >= 1100 px the terminal pane is on the left and the chat on the right, with a keyboard-operable splitter (arrow keys resize, Home/End snap). Below 1100 px the panes become tabs ("Screen", "Seance"), with new-activity indicators on the hidden tab.
- REQ-002: **Faithful 24x80 grid.** The terminal renders exactly 24 rows of 80 columns in a monospace face, one text row per row, cell geometry in `ch`/line-height units so `(row, col)` maps exactly to a position. It shows: protected text normally; intensified fields brighter; unprotected fields with a visible field marker (underline plus subtle fill, not colour alone); numeric fields marked; **hidden fields drawn as blank cells** (as a real 3270 does) with a "hidden field" marker only on hover/focus; the cursor as a block at `cursor`. Text is real DOM text (selectable, readable by assistive tech), not a canvas.
- REQ-003: **OIA line.** Below the grid, a 25th status line imitates the operator information area: connection state, read-only badge, `screen_id` short form, keyboard-locked/busy while a tool runs, replay badge in mock mode.
- REQ-004: **CRT effects with levels.** Phosphor green on near-black, soft glow, scanlines, vignette. An "Effects" control with `Full`, `Low`, `Off` (default `Low`). Text contrast stays AA with every level, including scanlines. Under `prefers-reduced-motion: reduce` there is no flicker, sweep or pulsing; the default level becomes `Off`-for-motion (static glow and scanlines allowed only at `Low`).
- REQ-005: **Planchette.** A lens-shaped pointer glides to the cell range of the field named by each `field_focus` event, with different gestures for `read` (slow sweep along the field), `fill` (settle, then a typing ripple) and `key` (hover at the key bar under the grid showing the key name). Events are queued in order; if the queue exceeds 5 the intermediate moves are skipped and only the latest is animated. It never covers the field text (a ring/lens, not a filled shape), is `pointer-events: none` and `aria-hidden` (its information is in the chat). With reduced motion it jumps instantly and shows a static ring.
- REQ-006: **Typing reveal.** When a `fill` result arrives, characters appear in the field progressively (up to 400 ms total); skipped under reduced motion or when more events are queued.

### Chat
- REQ-007: **Seance chat.** Messages (user, assistant, system), streaming via `assistant_delta`, final message on `assistant_message`. Plain text with a minimal, sanitised markdown subset (no raw HTML, no images, links shown but not auto-opened). Copy that is atmospheric ("The spirits are listening") must never replace a clear label for an action or a state.
- REQ-008: **Composer.** Multi-line input; Enter sends, Shift+Enter inserts a newline; Esc cancels the running turn (`cancel_turn`); disabled with a stated reason while disconnected or while a confirmation is open.
- REQ-009: **Step cards.** Inside the assistant message: collapsible cards for thinking summary, tool call (name, redacted arguments, business vs generic badge) and tool result (status, summary, trace). Text that came from the legacy screen is shown in an "untrusted legacy data" style (monospace, quoted, with a label) so a user can tell what the system said from what the agent said.

### Connection and states
- REQ-010: **Connect screen.** Lists systems from `GET /api/apps` as cards (name, kind: simulated or live, reachable or not, spirit-map and tool counts, read-only badge). Selecting one sends `connect_system`. Before a connection the terminal shows a dormant (powered-off) screen.
- REQ-011: **Websocket client.** `hello` with the session token, `last_seq` resume, backoff reconnect (1s, 2s, 4s, max 15s), duplicate and out-of-order events ignored by `seq`, a visible banner while reconnecting, and a full state reset when `session_id` changes.
- REQ-012: **Empty and error states**, each with a plain-language message and the next action: session lost (reconnect button), unknown screen (the `screen_id` is not in the spirit-map: an "uncharted" badge, the screen still renders), agent unreachable, LLM unavailable, tool error (code and message), no systems configured, expired confirmation, read-only server, observer-only connection (controls disabled with an explanation).

### Spirit-map, audit, confirmation
- REQ-013: **Spirit-map view.** A tab/overlay with the graph from `GET /api/apps/{app_id}/spirit-map` (`SpiritMapView`): nodes = screens (name, kind, confidence), edges = keys. The node matching the current `screen_id` is highlighted and follows the session; during a tool run the path taken is traced. Read-only edges are solid; denied or commit frontier edges are dashed with a lock mark and a text label (not colour alone); nodes with `needs_review` are marked. Selecting a node shows its screen preview, fields with business names and the tools that pass through it. Layout is deterministic (dagre) and rendered as SVG.
- REQ-014: **Accessible equivalent of the graph.** The same data as a table/list: screens, their outgoing keys and destinations, and tools. It is not hidden behind the graph; keyboard users can move between nodes with arrow keys and activate them with Enter.
- REQ-015: **Audit drawer.** A right-hand drawer (toggle button and shortcut) listing audit entries from `GET /api/audit` and live `audit_entry` events: time, seq, tool, short `screen_id`, field, value (as given, already redacted), key, outcome, `confirmed_by`. Filter by outcome (all, ok, pending/proposed, blocked, rejected). Shows the chain status from the REST response (`chain_ok`, `broken_seq`). Export as JSON. It is a non-modal complementary region; Esc closes it and returns focus to the toggle.
- REQ-016: **Confirmation modal: content.** Opened by `confirmation_required`. It shows, from the gate-sourced fields only: the **key** as a keycap, the **screen** (a miniature of the 24x80 screen with the fields from `field_snapshot` highlighted and their values listed, hidden/redacted values shown as such), the **time left**, and the read-only banner when `session_state.read_only` is true. The agent's own text (`agent_summary`) appears in a separate, clearly labelled block: "The agent says (unverified)". Authoritative facts and the agent's description are never mixed in one sentence.
- REQ-017: **Confirmation modal: behaviour.** `role="alertdialog"`, focus moves into it, focus is trapped, background is `inert`. **Deny is the initially focused control and Esc means Deny.** Approve is a separate, labelled button, disabled for 600 ms after the dialog opens, and only a trusted user event (`event.isTrusted`) can trigger it; Enter on the dialog does not approve unless Approve itself has focus. On expiry the modal switches to an "expired" state and closes with a message in the chat. It sends exactly one `confirm_decision`, shows pending/sent state, and displays the resolved outcome (`approved`, `denied`, `expired`, `blocked_read_only`, `stale`, `error`) from `confirmation_resolved`. If a new `confirmation_required` replaces it, the old one is shown as superseded.

### Accessibility, motion, security
- REQ-018: **Keyboard only.** Every function (connect, send, cancel, resize, tabs, spirit-map, audit drawer, confirmation) works without a mouse. Logical tab order, skip links ("Skip to chat", "Skip to screen"), landmarks (`header`, `main`, `aside`, `nav`), visible focus indicator with contrast >= 3:1, no keyboard traps except the modal's focus trap. Documented shortcuts, none single-key without a modifier except inside widgets.
- REQ-019: **Screen readers.** The chat is `role="log"` with `aria-live="polite"`; step cards announce briefly ("Reading the screen", "Filling Policy number") and at most once per second; confirmation uses an assertive announcement. The terminal pane is a labelled region whose rows are real text, with field labels exposed; a "Screen as text" toggle shows a linear description (title, fields, values, cursor). The graph has the table equivalent (REQ-014).
- REQ-020: **Visual accessibility.** Text >= 4.5:1, UI components and focus >= 3:1 against their background at every effects level; information never conveyed by colour or glow alone; works at 200% zoom and 400% reflow without losing function; honours `prefers-contrast: more` and `forced-colors`. Font sizes in `rem`.
- REQ-021: **Reduced motion.** `prefers-reduced-motion: reduce` disables glide, ripple, typewriter, flicker, graph path animation, panel slide transitions; they become instant state changes. An in-app "Reduce motion" toggle does the same regardless of OS setting.
- REQ-022: **Safe rendering.** All server text is rendered as text through React (no `dangerouslySetInnerHTML`); markdown is sanitised with an allow-list; hidden-field values are never in any DOM node, attribute or log; no secret in the bundle (`VITE_` variables are non-secret: agent URL only); the session token is kept in memory.
- REQ-023: **Mock and replay mode.** `VITE_MODE=mock` plays committed transcripts (`docs/contracts/examples/transcripts/*.jsonl`) through the same transport interface as the real websocket, so the UI is built and tested without the agent. Mock mode shows an unmissable `REPLAY` badge in the OIA line and header, so a replay can never be mistaken for a live session.
- REQ-024: **Performance.** A new `screen` event re-renders only changed rows; a screen update plus planchette move completes in one frame budget on a mid laptop; the graph with 50 nodes pans and selects smoothly.

## Testing
- REQ-025 (unit): Vitest + Testing Library for components: grid, OIA, planchette scheduler, chat, step cards, connect screen, audit drawer, modal.
- REQ-026 (property-based, `fast-check`, pinned): the event reducer: for any generated valid event sequence (including duplicates, reordering within the resume window, reconnects with new `session_id`) the state is consistent: no duplicate messages, a single open confirmation, no confirmation without a prior `confirmation_required`, `tool_result` always matched to a `tool_call`, hidden-value sentinel never present in state. And for the geometry: every `(row, col)` in 24x80 maps to a rectangle inside the grid and back to the same cell; field rectangles never overlap for non-overlapping fields; planchette targets stay inside the grid.
- REQ-027 (property-based): the planchette scheduler: for any sequence of `field_focus` events, the animated targets are a subsequence ending with the last event, at most one in flight, and with reduced motion the animation count is zero.
- REQ-028 (accessibility, automated): `vitest-axe` on each view and state, including the modal, empty and error states; focus-order and focus-trap tests for the modal and drawer; keyboard-only flow test (connect -> ask -> confirm -> deny).
- REQ-029 (safety): modal tests: Deny initially focused; Esc denies; Approve disabled for 600 ms; an untrusted (synthetic) click does not approve; `agent_summary` is never rendered inside the authoritative block; exactly one `confirm_decision` is sent per modal; expired modal cannot approve.
- REQ-030 (conformance): the transport and reducer accept every committed event example and transcript from `docs/contracts/examples/`; unknown event types are ignored without crashing and logged once.
- REQ-031 (manual, recorded in `web/A11Y.md`): screen reader pass (NVDA on Windows, VoiceOver if available), keyboard-only pass, 200%/400% zoom, forced-colors, reduced-motion, contrast measurements, with date, tool and result. Claims in the README say "designed to meet WCAG 2.2 AA" and link to this record; automated tools do not prove conformance.
- REQ-032 (visual): screenshots of the key states captured for the journal (connect, lookup in progress with planchette, confirmation modal, graph, audit drawer, session-lost).

## Non-goals
- No raw keyboard passthrough to the mainframe; no terminal emulation input.
- No editing of the spirit-map or tool approvals in the UI (CLI in spirit-map).
- No accounts, themes beyond the three effect levels and high-contrast support, or localisation in v1 (text lives in one strings module so it can be added).
- No direct access to the 3270 session or the MCP server.
