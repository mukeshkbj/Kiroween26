# Agent B journal (spirit-map)

Dated lines for the integrator to merge into `docs/kiro-journal.md`. One real surprise per stage.

- 2026-11-04 scaffold: the machine default is Python 3.14 but the project pins 3.12; `py -3.12 -m venv` fixed it. Every `pip`/`pytest` run prints "Could not find platform independent libraries <prefix>" on stderr, which PowerShell turns into exit code 1. Harmless; read the pytest summary line, not the exit code.
- 2026-11-04 policy: writing the mutation checks first paid off. Ten hand-made mutants of `policy.py` (drop a deny, let a text hint relax, allow before deny, ...) are each killed by one shared invariant function. Hypothesis alone would have taken far longer to find "hint relaxes".
- 2026-11-04 graph/store: `fake_insurance()` masks output fields with volatile regions for **every** screen, so those regions also cover static label text on other screens (the menu's `OPTION ===>` sits under the enquiry's `PREMIUM` region). Blanking volatile regions in stored rows erased the labels and every field became `field_2`. Fix: only a protected field whose span is *exactly* a volatile region counts as an output field and is blanked; everything else keeps its text.
- 2026-11-04 explorer, the interesting one: I wrote property tests that mutate the policy and expected the app-level safety property to fail. Six deny-rule mutants did. Two ("commit check removed", "declared keys apply on every screen") survived, and not by accident: candidate generation only ever tries *declared* commit keys, and the exploration gate reads the declarations straight from the data. Three layers disagree with a broken policy, so the app never sees the key. To kill them I had to widen candidates and open the gate, which is now a test. Defence in depth is real here, and the mutation tests say which layer saved us.
- 2026-11-04 explorer: `FakeApp.goto()` clears every named field of the target screen, including hidden ones. A test that expected a pre-filled hidden password to survive an ENTER failed until the rule used a no-op effect. A fake is part of the system under test; read its rules.
- 2026-11-04 field keys: the brief says the fake's keys are `option, polno, holder, status, premium, upddate, msg`. Keys derived from screen text can only be `option, polno, holder, status, premium, updated` and, for the unlabelled message line, `r22c1` (its cell). `upddate` and `msg` exist only inside the fake. The labeller/overrides step names them; recipes must refer to keys from the map, not from the fake.
- 2026-11-05: `.kiro/specs/spirit-map/design.md` changed
- 2026-11-04 labelling: the injection defence is almost anticlimactic because the label schema has no authority field to attack. A hostile model that returns `{"name": "ignore previous instructions", "read_only": true, "confidence": 1.0}` just gets a screen named "ignore previous instructions"; `read_only` is an extra key, dropped by the model. The test asserts the string `read_only` is absent from the whole labels dump. The real safety is structural: nothing downstream reads a label to decide a key.
- 2026-11-04 labelling: validators must *coerce* a bad confidence (clamp to [0,1]) but *reject* a non-string name, because a wrong-type name should drop the whole label to the heuristic, while a confidence of 5 is just enthusiasm. Getting that split right is what makes "drop and record" behave.
- 2026-11-04 6.1 spike (the one that mattered this week): `mcp` 2.3.0 derives a tool's advertised schema from the Python function signature, not from any schema you hand it. You *can* advertise a strict JSON Schema by overriding `Tool.parameters` after `Tool.from_function`, but the SDK still validates *calls* against the signature-derived metadata, so `maxLength`, `pattern`, `enum` and `additionalProperties` are advertised but not enforced by the SDK. The runtime must validate arguments itself. Built a handler with a generated signature from the input_schema so required/types are enforced by the SDK and the strict rules by us. No single-tool fallback needed. Recorded in design.md.
